## Проблема 1: шаги не обновлялись

Шаги, пришедшие утром (150), не обновлялись при следующих синхронизациях, даже если в Health Connect было 750.

**Причина:** в `/sync` действовало правило "fill-once" для `steps_1`/`steps_2` — перезаписывались только если текущее значение было `0`.

**Исправление (`app/main.py`, `/sync`):**
```python
# Было:
final_steps_1 = existing["steps_1"] if existing["steps_1"] else steps_1
final_steps_2 = existing["steps_2"] if existing["steps_2"] else steps_2

# Стало:
final_steps_1 = steps_1
final_steps_2 = steps_2
```

Fill-once оставлен **только** для `sleep_hours` — сон нельзя "переизмерить" в течение дня, а шаги — это счётчик, который должен накапливаться.

## Проблема 2: период синхронизации — раз в час

**Исправление (`SyncScheduler.kt`):**
```kotlin
private const val SYNC_INTERVAL_MINUTES = 5

PeriodicWorkRequestBuilder<SyncWorker>(
    SYNC_INTERVAL_MINUTES.toLong(), TimeUnit.MINUTES
)
```

**Важно:** WorkManager на Android имеет системный минимум для periodic work — на практике интервал округляется до **~15 минут**, независимо от того, что запрошено. Это подтверждено логами (`21:31:59` → `21:46:59`, ровно 15 мин) и является ожидаемым поведением платформы, а не багом.

## Проблема 3: well_being обнулялся при синхронизации

**Симптом:** пользователь вручную вводил `well_being` через веб-форму, но следующая автосинхронизация с телефона сбрасывала его в `0`.

**Причина:** `/sync` читал "текущее" состояние заметки (для merge — чтобы не затереть `well_being`/`alco`/"Заметки") из `NOTE_CACHE`. Кеш не инвалидируется при правках напрямую в Obsidian и не расшарен между воркер-процессами — поэтому мог отдать устаревшее (нулевое) значение `well_being`, которое затем и записывалось поверх реального.

**Исправление (`app/main.py`, `/sync`):**
```python
# Было:
content = get_note_cached(date)

# Стало:
content = obsidian.get_note_content(date)  # напрямую, минуя кеш
```

`NOTE_CACHE` оставлен только для отображения формы (`GET /`), где скорость важнее актуальности. Для merge-записи (`/sync`) корректность важнее — лишний REST-запрос к Obsidian раз в ~15 минут ничего не стоит.

## Проблема 4: related — единый индекс вместо помесячного

**Было:** `related: "[[55-sleepmon/index]]"` — захардкожено на весь проект.

**Стало:** строится динамически функцией `build_related_link(date_str)`:
```python
def build_related_link(date_str: str) -> str:
    year, month, _day = date_str.split("-")
    return f"[[55-sleepmon/{year}/index-{month}.md]]"
```
Пример: для `2026-08-26` → `[[55-sleepmon/2026/index-08.md]]`. Пересчитывается на каждой записи (`/save` и `/sync`) — самоисправляется, если раньше было записано неверно.

**Требование:** помесячные индексные заметки (`55-sleepmon/2026/index-08.md` и т.д.) должны существовать заранее с dataview-запросом — приложение их не создаёт, только ссылается.

## ⚠️ Отдельная находка: почему изменения "не применялись" несмотря на пересборку

После всех вышеописанных правок какое-то время сохранялась путаница: код в vault поправлен, `docker compose up -d --build app` выполнен — а поведение на сервере оставалось старым (например, `related` у части карточек снова стал `[[55-sleepmon/index]]`).

**Причина:** vault-папка (`10-projects/sleep-monitor`) и серверная deploy-папка (`~/vsuh-helor-conf/services/opt/sleepmon/`) — это **два независимых git-чекаута одного репозитория** `vsuh/sleepmon`, а не общий примонтированный путь и не то, что синхронизируется автоматически. `docker compose up -d --build app` честно пересобирает образ — но из того состояния файлов, что **уже закоммичено и запушено** в deploy-чекауте на сервере.

**Правильная последовательность деплоя:**
```bash
# 1. В vault-чекауте (или откуда правится код):
git add . && git commit -m "..." && git push

# 2. На сервере, В DEPLOY-ЧЕКАУТЕ:
cd ~/vsuh-helor-conf/services/opt/sleepmon
git pull
git log -1 --oneline   # сверить, что коммит совпадает с тем, что запушен

# 3. Только теперь пересборка:
docker compose up -d --build app
docker compose logs -f app
```

Если после `git pull` `git log -1 --oneline` на сервере не совпадает с коммитом в vault-чекауте — значит пуш ещё не дошёл или `pull` тянет не ту ветку. Проверяется командой `git remote -v` и `git branch --show-current` в обоих чекаутах.
