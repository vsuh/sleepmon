# Промпт: веб-приложение "Sleep Monitor" для ведения дневника самочувствия в Obsidian

## Контекст и цель

Нужно веб-приложение, которое каждый день позволяет быстро занести данные о сне, активности и самочувствии в заметку внутри Obsidian-vault. Источник данных — умный браслет Xiaomi (Mi Band) через приложение **Mi Fitness**, плюс ручной ввод/коррекция субъективных показателей.

Пользователь один (single-user, не multi-tenant). Приложение — личный инструмент, не продукт.

---

## 1. Архитектура

- Сервер: **Ubuntu 24.04**, всё разворачивается через **Docker Compose**.
- Obsidian-vault физически синхронизируется на этот сервер через **Syncthing** (уже настроено, вне зоны ответственности этого проекта).
- Плагин **Local REST API** (coddingtonbear/obsidian-local-rest-api) должен быть включён в vault и обслуживать HTTPS на порту `27124` (self-signed сертификат).
- Поскольку у Obsidian нет официального headless-режима без подписки Obsidian Sync (а тут используется Syncthing, не Obsidian Sync), Obsidian нужно поднять как **реальное Electron-приложение внутри виртуального X-дисплея (Xvfb)** в отдельном Docker-контейнере — по паттерну образов вроде `sytone/obsidian-remote` (Xvfb + noVNC для разовой ручной настройки/логина в плагин через VNC-доступ из браузера).
- Веб-приложение (бэкенд + фронтенд) — отдельный сервис в том же docker-compose, ходит к Obsidian-контейнеру по внутренней docker-сети на `https://obsidian:27124` (или аналогичное имя сервиса), API-ключ Local REST API передаётся через переменную окружения/`.env`, TLS-проверку самоподписанного сертификата отключить для внутреннего запроса (`verify=False` на стороне клиента, т.к. трафик не покидает Docker-сеть).
- **Не писать в vault напрямую по файловой системе** — только через Local REST API, чтобы Obsidian видел изменения через свой live-кеш метаданных, а не спотыкался о рассинхрон при внешней записи файлов.

### Docker Compose — ожидаемые сервисы
1. `obsidian` — headless Obsidian с примонтированным vault-volume (путь к синхронизированной Syncthing-папке) и включённым плагином Local REST API.
2. `app` — бэкенд + отдаваемый им фронтенд (или отдельный сервис фронтенда, на усмотрение реализации).
3. `.env` с переменными: `OBSIDIAN_API_KEY`, `OBSIDIAN_BASE_URL`, `APP_PIN` (пароль входа в приложение), `MIFIT_*` (креды/токен для Mi Fitness, см. раздел 4).

## 2. Структура данных заметки

### Расположение и именование файлов
```
55-sleepmon/<YYYY>/<YYYY-MM-DD>.md
```
Например: `55-sleepmon/2026/2026-08-07.md`. Папка по году создаётся автоматически при первой записи года.

### Frontmatter (YAML)
```yaml
---
project: "sleepmon"
created: "2026-08-07"
related: "[[sleep-monitor]]"
sleep_hours: 7.5          # float, длительность сна в часах
pulse_avg_day: 68         # int, средний пульс за день (бодрствование)
pulse_avg_sleep: 58       # int, средний пульс во время сна (ночной)
steps_1: 3200              # int, шаги за первую половину дня
steps_2: 4100               # int, шаги за вторую половину дня
steps_total: 7300           # int, сумма steps_1 + steps_2 (хранить явно, не только вычислять)
well_being: 7               # int, 0-10, субъективная оценка самочувствия
alco: false                 # bool, был ли алкоголь в этот день
---
```

Это финальная, уже согласованная схема полей — заменяет черновой шаблон `_templates/src/dl-auto.md` (там были нерасшифрованные поля вроде `alco: [true,false]`, тестовый мусор `steps_2: 2` и неясная семантика `steps_1/2`). Не переиспользовать черновик буквально, взять за основу только сам факт существования темплейта и связку `related: "[[sleep-monitor]]"` (используется в существующем dataview-индексе `55-sleepmon/sleep-monitor.md`, который перечисляет все заметки проекта — сохранить эту связь, чтобы индекс продолжал работать).

### Тело заметки
После frontmatter — свободный текстовый раздел для субъективных заметок:
```markdown
## Заметки

(текст пользователя: как спалось, симптомы, комментарии — произвольный markdown)
```

### Границы MVP
Никакой аналитики/графиков/статистики внутри самого веб-приложения не нужно — для этого у пользователя уже есть Obsidian + Dataview (см. `55-sleepmon/sleep-monitor.md`). Приложение — это чистый ввод/редактирование данных.

## 3. Пользовательский сценарий (UI/UX)

Однопользовательское веб-приложение, доступное в локальной сети (LAN), мобильный и десктопный доступ.

1. **Вход**: простой общий PIN/пароль на всё приложение (без сложной модели пользователей — один секрет, хранится как хэш в `.env`/конфиге, сессия через cookie).
2. **Главный экран — сегодняшняя запись**:
   - Кнопка **"Загрузить данные"** — тянет сон/пульс/шаги из Mi Fitness за нужный период (см. раздел 4), заполняет поля формы.
   - Форма с полями из frontmatter выше: числовые инпуты/слайдеры для `sleep_hours`, `pulse_avg_day`, `pulse_avg_sleep`, `steps_1`, `steps_2` (`steps_total` можно посчитать автоматически на фронте, но сохранять как отдельное поле), слайдер/шкала 0-10 для `well_being`, чекбокс для `alco`, текстовое поле для раздела "Заметки".
   - Если данные с браслета не подтянулись (ошибка авторизации/сети) — форма всё равно доступна для полностью ручного заполнения, ничего не блокирует сохранение.
   - Кнопка **"Сохранить"** — создаёт/обновляет заметку за сегодня через Local REST API (`PUT /vault/{path}` с полным содержимым, frontmatter + тело).
3. **Навигация по прошлым дням**: простой выбор даты (календарь/список), открывает ту же форму, предзаполненную текущим содержимым заметки этого дня (читается через `GET /vault/{path}`), позволяет править и пересохранять. При переходах между датами, данные беруться из локального кеша, кеш за 5 дней заполняется при загрузке страницы (в фоне). Если в кеше нет данных, то они запрашиваются из Google Fit.

4. **Массовый бэкфилл**: отдельный экран/режим — выбор диапазона дат, приложение подряд тянет данные из Mi Fitness за каждый день диапазона и создаёт/обновляет заметки пакетно, с отчётом об успехах/ошибках по каждой дате (частичный сбой на одном дне не должен прерывать весь батч).

## 4. Интеграция с Google Fit API ✅ РЕАЛИЗОВАНО

От прямой интеграции с закрытым API Xiaomi Wear было решено отказаться (нет официального API, требуется нестабильный reverse-engineering). Данные получаем через **Google Fit API** (официальный, поддерживается Google).

**Требование к настройке**: приложение Mi Fitness должно быть настроено для синхронизации данных с Google Fit на телефоне пользователя (через раздел «Сторонние приложения» в Mi Fitness). После этого данные браслета (сон, шаги, пульс) появляются в Google Fit и становятся доступны через API.

**Реализация** (файл `app/google_fit.py`):
- OAuth 2.0 авторизация: `credentials.json` (скачан из Google Cloud Console) + `token.json` (генерируется при первом запуске).
- Используемые scopes: `fitness.activity.read`, `fitness.sleep.read`, `fitness.heart_rate.read`.
- Функции: `fetch_steps()`, `fetch_heart_rate()`, `fetch_sleep()` — запросы к `users.dataset.aggregate` и `users.sessions.list`.
- Функция `fetch_day_data(date_str)` — точка входа для бэкенда, возвращает словарь с данными или `None` при ошибке.

**Важно**: код изолирован в отдельном модуле, сбой не роняет приложение — при ошибке форма остаётся доступна для ручного ввода.

### Вариант А — прямой логин по паролю (Huami/старый Mi Fit флоу)
Работает для аккаунтов, привязанных к старому Mi Fit/Zepp Life login-флоу: POST на `https://account.huami.com/v2/client/login` с email/паролем → получаем `access token` → обмен на `login_token`/`apptoken` → запросы к `https://api-mifit.huami.com/v1/data/band_data.json` за нужные даты (в ответе — сон по фазам, шаги, пульс). Референс-реализация: `micw/hacking-mifit-api` (Python).

### Вариант Б — перехваченный apptoken (актуально для новых аккаунтов Mi Fitness)
У пользователя именно **Mi Fitness** (новое приложение), где прямой логин по паролю зачастую не работает/заблокирован анти-фрод защитой Xiaomi. В этом случае:
1. Один раз вручную перехватить `apptoken` из трафика приложения на телефоне через HTTP-прокси (HTTP Toolkit / Fiddler) при обычном входе в Mi Fitness.
2. Сохранить `apptoken` (и `user_id`, региональный хост) в конфиге приложения.
3. Использовать тот же `api-mifit*.huami.com`/`api-mifit*.zepp.com` эндпоинт для получения данных за конкретный день.
4. Токен со временем протухает — предусмотреть в UI/конфиге простое место для ручного обновления токена (например, поле в настройках приложения), а не жёстко зашитый в коде секрет.

**Требование к реализации**: заложить оба варианта как стратегию с автоматическим фолбэком — сперва попробовать логин по паролю (Вариант А), при ошибке/неподдерживаемом флоу — использовать сохранённый вручную `apptoken` (Вариант Б). Обязательно логировать, какой из способов сработал, чтобы было понятно при отладке.

**Важно**: это неофициальные эндпоинты, могут измениться без предупреждения — код интеграции должен быть изолирован в отдельном модуле/адаптере, чтобы его было легко чинить отдельно от остального приложения, и не должен ронять всё приложение при сбое (см. UI-сценарий выше — ручной ввод должен работать всегда, независимо от Mi Fitness).

## 5. Технологический стек

- Бэкенд: **Python (FastAPI)** — естественный выбор, так как все референсные реализации интеграции с Mi Fitness/Huami API написаны на Python, что упростит адаптацию кода.
- Фронтенд: простой, без излишеств — server-rendered формы или лёгкий SPA (на усмотрение реализации), с адаптивной вёрсткой под мобильный экран (сценарий "открыл с телефона, нажал кнопку, сохранил").
- Хранение токена Mi Fitness и PIN-хэша — в конфиге/`.env`, не в коде.
- HTTP-клиент к Obsidian Local REST API — с явным отключением проверки TLS для внутреннего самоподписанного сертификата.

## 6. Нефункциональные требования

- Все временные метки — с учётом таймзоны сервера (Ubuntu-сервер, единая для всего проекта; отдельная многочасовая поддержка не нужна).
- Устойчивость к недоступности Obsidian-контейнера: понятная ошибка пользователю, данные формы не теряются при неудачном сохранении (возможность повторить попытку).
- Устойчивость к недоступности/сбою Mi Fitness API: приложение остаётся полностью функциональным для ручного ввода.
- Секреты (PIN-хэш, API-ключ Local REST API, токен Mi Fitness) — только через переменные окружения/`.env`, не коммитить в репозиторий.
- Docker Compose должен подниматься одной командой (`docker compose up`) и быть самодостаточным (включая headless Obsidian с уже примонтированным vault и включённым плагином — если первичная настройка плагина требует ручных кликов через VNC, явно задокументировать этот шаг в README).

  - Вызывается безусловно в `MainActivity.onCreate()` (не только по кнопке) — синхронизация продолжает идти в фоне после закрытия приложения.
  - `BootReceiver.kt` + `RECEIVE_BOOT_COMPLETED` в манифесте — переустанавливает задачу после перезагрузки телефона (подстраховка от OEM-прошивок, чистящих очередь WorkManager при загрузке).
  - `SyncWorker` теперь синхронизирует последние 2 дня (сегодня + вчера) каждый час — этого достаточно, чтобы поймать ночной сон, который иногда попадает в Health Connect только после пробуждения.
- **Резервный адрес сервера**:
  - В настройках приложения два поля: **Server URL (основной)** и **Server URL (резервный)** — по умолчанию `https://sm.vsuh.duckdns.org:9124`.
  - `SyncHelper.resolveActiveServer()` — пробует основной адрес с таймаутом **5 секунд** (`connectTimeout`/`readTimeout`/`callTimeout` в OkHttp), при неудаче/таймауте переключается на резервный. Выбранный адрес используется для всех дней синхронизации в рамках одного запуска.
  - Требуется настроить на HRLOR nginx reverse-proxy: `sm.vsuh.duckdns.org:9124` → `app:8000` (пробрасывает на тот же FastAPI-инстанс, что и локальный `192.168.x.x:8000`).




## Разделение /save и /sync, защита ручных полей (2026-08-16, продолжение)
- **Диагностика пульса/сна**: подтверждено, что источник Mi Fitness → Health Connect иногда "залипает" — после отключения/включения синхронизации Health Connect внутри Mi Fitness и повторного `Sync Now` часть пропавших данных подтянулась. Это внешняя проблема Mi Fitness, не связана с кодом приложения; штатного лечения на нашей стороне нет, кроме периодического ручного тыка в Mi Fitness при провалах.
- **Баг**: `/save` использовался и для ручной формы, и для автосинхронизации с телефона — Android-приложение раз в час затирало `well_being` (на дефолтные 5), `alco` (на false) и `Заметки` (на "Synced from Android Companion"), стирая ручные правки пользователя.
- **Исправление** — разделены два endpoint'а в `main.py`:
  - `/save` — используется только веб-формой (кнопка "Сохранить"), полная перезапись, поведение не изменилось.
  - `/sync` (новый) — используется только Android-приложением. Читает текущую заметку через `parse_note()` и **сливает** новые значения: `sleep_hours`/`pulse_avg_day`/`pulse_avg_sleep`/`steps_1`/`steps_2`/`steps_total` обновляются всегда; `alco` и `Заметки` никогда не перезаписываются; `well_being` сохраняется как есть, если он не `0` (0 трактуется как "ещё не оценено").
  - `sleep_hours` теперь всегда округляется до 1 знака после запятой (`round(sleep_hours, 1)`) в обоих endpoint'ах.
  - Android `SyncHelper.postToServer()` переключён с `POST /sync` на новый маршрут, поля `well_being`/`alco`/`notes` больше не отправляются с телефона вообще.
- **Вопрос про формулы в frontmatter**: YAML frontmatter — статичные данные, Obsidian их не вычисляет. `steps_total: "steps_1+steps_2"` сохранился бы буквальной строкой, а не как выражение. Решение остаётся прежним — сервер сам считает `steps_total` при каждой записи.




## Уточнение правила merge для /sync — "заполнить один раз" (2026-08-16, продолжение)
- Изменена логика `/sync`: `sleep_hours`, `steps_1`, `steps_2` (и производный `steps_total`) стали **fill-once полями** — перезаписываются только если текущее значение в карточке равно `0`, и только ненулевым значением с телефона. После того как значение зафиксировано (не 0), синхронизация его больше не трогает — изменить можно только вручную через веб-форму (`/save`).
- `pulse_avg_day` / `pulse_avg_sleep` в это правило не входят — обновляются при каждой синхронизации, т.к. это естественно колеблющиеся показания, а не разово фиксируемое значение.
- `well_being`/`alco`/`notes` — поведение не изменилось (см. предыдущую запись).
- `parse_note()` расширен: теперь возвращает также `sleep_hours`, `steps_1`, `steps_2` из текущей заметки для merge-проверки.
