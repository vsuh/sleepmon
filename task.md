# Промпт: веб-приложение "Sleep Monitor" для ведения дневника самочувствия в Obsidian

## Контекст и цель

Нужно веб-приложение, которое каждый день позволяет быстро занести данные о сне, активности и самочувствии в заметку внутри Obsidian-vault. Источник данных — умный браслет Xiaomi (Mi Band) через приложение **Mi Fitness**, плюс ручной ввод/коррекция субъективных показателей.

Пользователь один (single-user, не multi-tenant). Приложение — личный инструмент, не продукт.

---

## 1. Архитектура

- Сервер: **Ubuntu 24.04**, всё разворачивается через **Docker Compose**.
- Obsidian-vault физически синхронизируется на этот сервер через **Syncthing** (уже настроено, вне зоны ответственности этого проекта).
- Плагин **Local REST API** (coddingtonbear/obsidian-local-rest-api) должен быть включён в vault и обслуживать HTTPS на порту `27124` (self-signed сертификат).
- Поскольку у Obsidian нет официального headless-режима без подписки Obsidian Sync (а тут используется Syncthing, не Obsidian Sync), Obsidian нужно поднять как **реальное Electron-приложение внутри виртуального X-дисплея (Xvfb)** в отдельном Docker-контейнере — по паттерну образов вроде `sytone/obsidian-remote` (Xvfb + noVNC для разовой ручной настройки/логина в плагин через VNC-доступ из браузера).
- Веб-приложение (бэкенд + фронтенд) — отдельный сервис в том же docker-compose, ходит к Obsidian-контейнеру по внутренней docker-сети на `https://obsidian:27124` (или аналогичное имя сервиса), API-ключ Local REST API передаётся через переменную окружения/`.env`, TLS-проверку самоподписанного сертификата отключить для внутреннего запроса (`verify=False` на стороне клиента, т.к. трафик не покидает Docker-сеть).
- **Не писать в vault напрямую по файловой системе** — только через Local REST API, чтобы Obsidian видел изменения через свой live-кеш метаданных, а не спотыкался о рассинхрон при внешней записи файлов.

### Docker Compose — ожидаемые сервисы
1. `obsidian` — headless Obsidian с примонтированным vault-volume (путь к синхронизированной Syncthing-папке) и включённым плагином Local REST API.
2. `app` — бэкенд + отдаваемый им фронтенд (или отдельный сервис фронтенда, на усмотрение реализации).
3. `.env` с переменными: `OBSIDIAN_API_KEY`, `OBSIDIAN_BASE_URL`, `APP_PIN` (пароль входа в приложение), `MIFIT_*` (креды/токен для Mi Fitness, см. раздел 4).

### ⚠️ Деплой: два git-чекаута одного репозитория (актуально с 2026-08-26)
Vault-папка (`10-projects/sleep-monitor`, синхронизируется через Syncthing на Windows-десктоп) и серверная deploy-папка (`~/vsuh-helor-conf/services/opt/sleepmon/` на HRLOR) — это **два независимых git-чекаута одного и того же репозитория** `vsuh/sleepmon` (ветка `master`), а НЕ общий примонтированный путь и не ручная копия файлов.

Следствие: правка `app/main.py` (или любого файла) в vault-чекауте **не появляется** на сервере автоматически. Обязательная последовательность перед любым `docker compose up -d --build app`:
1. В vault-чекауте: `git add`, `git commit`, `git push`.
2. В deploy-чекауте на сервере: `git pull` (сверить `git log -1 --oneline` — коммиты должны совпадать).
3. Только после этого — `docker compose up -d --build app`.

Пропуск шага 2 — самая частая причина "я поправил код, а поведение не изменилось": Docker честно пересобирает образ, но из **старого закоммиченного состояния**, которое уже лежит в deploy-чекауте.

### ⚠️ Часовой пояс в контейнере `app` (актуально с 2026-08-26)
`docker-compose.yml` задаёт `TZ=Europe/Moscow` для сервиса `app`, но база `python:3.11-slim` не включает пакет `tzdata` (Debian slim-образы вырезают его для экономии места) — без файлов `/usr/share/zoneinfo` переменной `TZ` физически не из чего брать смещение, поэтому время внутри контейнера (и в `docker compose logs -t`) остаётся в UTC несмотря на настройку. Это же касается и логов самого приложения, если они не сконфигурированы явно.

Также важно понимать: `docker compose logs -t` печатает **собственную метку времени Docker-демона** (всегда UTC, на уровне хоста), которая не зависит от `TZ` контейнера в принципе — эта метка не станет московской, даже если внутри контейнера всё настроено правильно. Чтобы видеть корректное локальное время, нужно смотреть на метки времени, которые печатает **само приложение** (через `logging`), и запускать `docker compose logs -f app` **без** `-t`.

Исправлено (`app/Dockerfile`): установлен `tzdata`, `ENV TZ=Europe/Moscow` продублирован на уровне образа; `app/main.py` явно конфигурирует `logging` с `time.localtime` в качестве конвертера времени, так что метки в собственных логах приложения (`%(asctime)s`) идут по локальному (московскому) времени.

## 2. Структура данных заметки

### Расположение и именование файлов
```
55-sleepmon/<YYYY>/<MM>/<YYYY-MM-DD>.md
```
Например: `55-sleepmon/2026/08/2026-08-26.md`. Папки по году и месяцу создаются автоматически при первой записи (Obsidian Local REST API создаёт недостающие директории на `PUT`).

> Ранее (до 2026-08-16) использовалась плоская схема `55-sleepmon/<YYYY>/<YYYY-MM-DD>.md` без подпапки месяца — заменена на `<YYYY>/<MM>/<YYYY-MM-DD>.md` для более удобной месячной группировки. Реализовано в `_note_path()` (`app/obsidian.py`).

### Frontmatter (YAML)
```yaml
---
project: "sleepmon"
created: "2026-08-26"
related: "[[55-sleepmon/2026/index-08.md]]"
sleep_hours: 7.5          # float, длительность сна в часах
pulse_avg_day: 68         # int, средний пульс за часы бодрствования (не за весь календарный день — см. ниже)
pulse_avg_sleep: 58       # int, средний пульс во время сна (в границах самой сессии сна)
steps_1: 3200              # int, шаги за первую половину дня
steps_2: 4100               # int, шаги за вторую половину дня
steps_total: 7300           # int, сумма steps_1 + steps_2 (хранить явно, не только вычислять)
sleep_light_min: 210         # int, минуты в фазе лёгкого сна
sleep_deep_min: 85           # int, минуты в фазе глубокого сна
sleep_rem_min: 95            # int, минуты в фазе REM
sleep_awake_min: 15          # int, минуты пробуждений внутри сессии сна
well_being: 7               # int, 0-10, субъективная оценка самочувствия
alco: false                 # bool, был ли алкоголь в этот день
---
```

Это финальная, уже согласованная схема полей — заменяет черновой шаблон `_templates/src/dl-auto.md` (там были нерасшифрованные поля вроде `alco: [true,false]`, тестовый мусор `steps_2: 2` и неясная семантика `steps_1/2`). Не переиспользовать черновик буквально, взять за основу только сам факт существования темплейта.

> **`related` (актуально с 2026-08-26):** больше не хардкодится единой строкой на весь проект. Строится динамически функцией `build_related_link(date_str)` в `app/main.py` как ссылка на **помесячный** индекс: `[[55-sleepmon/<YYYY>/index-<MM>.md]]` (месяц дополняется нулём слева до двух символов). Пересчитывается заново при каждой записи (`/save` и `/sync`), поэтому самоисправляется, если когда-то был записан неверно. Требует, чтобы помесячные индексные заметки (`index-08.md` и т.д.) существовали и содержали dataview-запрос по этой ссылке — сами по себе индексные заметки приложением не создаются.
>
> Более ранняя версия схемы использовала единый индекс `related: "[[55-sleepmon/index]]"` (или `[[sleep-monitor]]` в самой первой версии) — устарело, см. журнал изменений в конце документа.

> **`pulse_avg_day` / `pulse_avg_sleep` (пересчитано 2026-08-26):** изначально считались как единое среднее по всему календарному дню (00:00–24:00), что занижало значение из-за естественно более низкого пульса во сне и не совпадало с "средним пульсом", который показывает Mi Fitness. Теперь `pulse_avg_day` считается только по окну **от пробуждения до конца суток** (часы бодрствования), а `pulse_avg_sleep` — по фактическому окну самой сессии сна. Оба поля НЕ fill-once — обновляются на каждой синхронизации.

> **Фазы сна (`sleep_light_min`/`sleep_deep_min`/`sleep_rem_min`/`sleep_awake_min`, добавлено 2026-08-26):** читаются из `SleepSessionRecord.stages` в Health Connect (та же запись, что даёт `sleep_hours` — отдельное разрешение не требуется). Делят fill-once-семантику с `sleep_hours`: заполняются один раз за ночь и не пересчитываются в течение дня. `sleep_awake_min` объединяет фазы AWAKE/AWAKE_IN_BED/OUT_OF_BED внутри сессии сна. Если устройство/приложение-источник не размечает фазы (некоторые браслеты отдают только один общий блок сна) — все четыре поля останутся `0`, это фиксируется в логах Android-приложения как предупреждение, не как ошибка.

### Тело заметки
После frontmatter — свободный текстовый раздел для субъективных заметок:
```markdown
## Заметки

(текст пользователя: как спалось, симптомы, комментарии — произвольный markdown)
```

### Границы MVP
Никакой аналитики/графиков/статистики внутри самого веб-приложения не нужно — для этого у пользователя уже есть Obsidian + Dataview. Приложение — это чистый ввод/редактирование данных.

## 3. Пользовательский сценарий (UI/UX)

Однопользовательское веб-приложение, доступное в локальной сети (LAN), мобильный и десктопный доступ.

1. **Вход**: простой общий PIN/пароль на всё приложение (без сложной модели пользователей — один секрет, хранится как хэш в `.env`/конфиге, сессия через cookie).
2. **Главный экран — сегодняшняя запись**:
   - Форма с полями из frontmatter выше: числовые инпуты/слайдеры для `sleep_hours`, `pulse_avg_day`, `pulse_avg_sleep`, `steps_1`, `steps_2` (`steps_total` можно посчитать автоматически на фронте, но сохранять как отдельное поле), слайдер/шкала 0-10 для `well_being`, чекбокс для `alco`, текстовое поле для раздела "Заметки". Поля фаз сна на форме не редактируются вручную — управляются только синхронизацией (см. раздел 4), но сохраняются при ручном `/save` (сервер подтягивает текущие значения из Obsidian перед перезаписью, чтобы их не потерять).
   - Кнопка **"Сохранить"** — создаёт/обновляет заметку за сегодня через Local REST API (`PUT /vault/{path}` с полным содержимым, frontmatter + тело). Это единственный путь, которым можно менять `well_being`, `alco` и текст "Заметки" — Android-синхронизация их никогда не трогает (см. раздел про `/sync`).
3. **Навигация по прошлым дням**: простой выбор даты (календарь/список), открывает ту же форму, предзаполненную текущим содержимым заметки этого дня (читается через `GET /vault/{path}`), позволяет править и пересохранять. При переходах между датами, данные берутся из локального кеша, кеш за 5 дней заполняется при загрузке страницы (в фоне).
4. **Массовый бэкфилл**: реализован на стороне Android-приложения (см. раздел 4) — выбор диапазона дат, приложение подряд тянет данные из Health Connect за каждый день диапазона и шлёт их на `/sync`, с отчётом об успехах/ошибках по каждой дате в статус-строке (частичный сбой на одном дне не прерывает весь батч).

## 4. Источник данных: Android Companion App (Health Connect) ✅ РЕАЛИЗОВАНО

От Google Fit API отказались (Cloud API для Fit устарел/ограничен), от прямой интеграции с закрытым API Xiaomi Wear — тоже (нет официального API). Данные получаем через **Health Connect** — системное Android API, куда Mi Fitness сама пишет данные браслета (шаги, сон, пульс), если это явно включено в настройках Mi Fitness («Сторонние приложения» → Health Connect, разрешения Steps/Sleep/Heart Rate).

**Реализация — отдельное Android-приложение** `android_sync_app/` (`com.example.sleepmonitorsync`):
- Читает `StepsRecord`, `SleepSessionRecord` (включая разбивку по фазам `stages`), `HeartRateRecord` из Health Connect за указанный день.
- Порядок чтения: сначала сон (чтобы знать окно пробуждения/сна), затем шаги, затем пульс двумя отдельными запросами — за часы бодрствования и за время сна.
- Шлёт данные на сервер (`POST /sync`) — либо вручную ("Sync Now"), либо в диапазоне дат ("Sync Range" — бэкфилл), либо автоматически в фоне через `WorkManager` (см. ниже).
- Логирование в `SyncHelper.kt`: подробные структурированные логи для каждого шага синхронизации (резолв сервера, чтение каждой метрики отдельно, отправка на сервер, итог) — облегчает диагностику при разборе `adb logcat`.

**Фоновая синхронизация:**
- `SyncScheduler.kt` планирует периодический `SyncWorker` через `WorkManager`. Запрошенный интервал — **5 минут** (`ExistingPeriodicWorkPolicy.UPDATE`), но фактический интервал на устройстве определяется системным минимумом Android для periodic work и может округляться до **15 минут** — это ожидаемое поведение платформы, не баг приложения.
- `BootReceiver.kt` переустанавливает задачу после перезагрузки телефона.
- `SyncWorker` синхронизирует последние 2 дня (сегодня + вчера) при каждом запуске — этого достаточно, чтобы поймать ночной сон, попадающий в Health Connect иногда только после пробуждения.

**Резервный сервер:** приложение хранит два адреса (основной + резервный), пробует основной с таймаутом 5 сек, при неудаче на весь прогон переключается на резервный. Оба адреса ведут на **один и тот же** Docker-контейнер `app` (разные внешние точки входа — LAN IP и duckdns через reverse-proxy), поэтому расхождений в поведении между ними быть не должно.

**Важно**: если Mi Fitness перестаёт писать данные (особенно пульс) в Health Connect — это внешняя проблема синхронизации Mi Fitness↔Health Connect, не связанная с кодом приложения. Штатное лечение: отключить/включить интеграцию Health Connect в настройках Mi Fitness и повторить `Sync Now`.

## 5. Технологический стек

- Бэкенд: **Python (FastAPI)**, образ `python:3.11-slim` с явно доустановленным `tzdata` (см. раздел 1 про часовой пояс).
- Android: **Kotlin**, Health Connect Client, WorkManager, OkHttp.
- Фронтенд веб-приложения: простой server-rendered Jinja2, адаптивная вёрстка под мобильный экран.
- Хранение PIN-хэша — в конфиге/`.env`, не в коде.
- HTTP-клиент к Obsidian Local REST API — с явным отключением проверки TLS для внутреннего самоподписанного сертификата.

## 6. Нефункциональные требования

- Все временные метки — с учётом таймзоны сервера (`Europe/Moscow`, настраивается через `TZ` в `docker-compose.yml` + `tzdata` в образе, см. раздел 1). Собственные логи приложения (`logging` в `main.py`) печатают локальное время явно; метки `docker compose logs -t` остаются в UTC независимо от настройки — это особенность Docker, а не баг приложения.
- Устойчивость к недоступности Obsidian-контейнера: `/sync` при `ObsidianFetchError` прерывается с `502` и **ничего не пишет** (не путает "не смог прочитать" с "заметки нет" — см. журнал 2026-08-16). Форма (`GET /`) при той же ошибке просто показывает пустые поля, ручной ввод остаётся доступен.
- Секреты (PIN-хэш, API-ключ Local REST API) — только через переменные окружения/`.env`, не коммитить в репозиторий.
- Docker Compose должен подниматься одной командой (`docker compose up`) и быть самодостаточным (включая headless Obsidian с уже примонтированным vault и включённым плагином — если первичная настройка плагина требует ручных кликов через VNC, явно задокументировать этот шаг в README).

### Переход на Bluetooth Classic SPP (2026-08-30)

Диагностика на реальном 9 Pro показала: BLE GATT-сервис `0000fe95` у этого браслета содержит только характеристики `0050/005e/005f` (не `0051/0052/0053/0055`), а прямое BLE-подключение зависает без единого GATT-коллбэка после того, как браслет уже сопряжён на уровне ОС (в списке Bluetooth "Paired devices"). Это совпадает с официальной оговоркой Gadgetbridge (gadgetbridge.org/basics/topics/xiaomi-protobuf/): часть Xiaomi-устройств использует **Bluetooth Classic SPP** вместо BLE GATT для командного канала, в зависимости от прошивки.

Подтверждено по исходникам Gadgetbridge (классы `XiaomiSppSupport`/`XiaomiSppPacketV1`/`XiaomiSppProtocolV1`, которых не было в моём изначальном декабрьском GitHub-зеркале — взял через `api.github.com`/актуальный поиск): реализован новый транспорт поверх `BluetoothSocket` + RFCOMM на стандартном SPP UUID `00001101-...`.

Новые файлы:
- `.../band/XiaomiSppFrame.kt` — фрейминг потокового RFCOMM-канала (преамбула `BA DC FE`, каналы Version/ProtoRX/ProtoTX, dataType Plain/Encrypted/Auth, инкрементальная сборка кадров из потока байт)
- `.../band/XiaomiBandClassicConnection.kt` — сама логика: подключение сокета (браслет должен быть уже сопряжён в настройках Android), фоновый поток чтения, запрос версии протокола (с 5-секундным фолбэком, как в оригинале), тот же 3-шаговый auth handshake, что и в BLE-варианте (переиспользует `XiaomiCrypto`/`XiaomiProto`)

`XiaomiBandTester` переключён на использование `XiaomiBandClassicConnection`. `XiaomiBandConnection` (BLE GATT) оставлен в проекте на случай, если для других устройств/прошивок понадобится именно BLE-путь.

**Важно:** реализована только протокольная версия SPP v1 (Gadgetbridge переключается на v2-фрейминг, если браслет в ответе на version-запрос сообщает версию ≥2 — v2 не портирован, в логе будет предупреждение, если это применимо к 9 Pro).

Не проверено на реальном железе — ждём результата следующего теста.

### Протокол V2 подтверждён через HCI snoop log (2026-09-14) — Этап A завершён (ожидает финального теста)

Сняли `btsnoop_hci.log` во время реальной работы Mi Fitness с браслетом, разобрали через `tshark` (протокольный анализатор Wireshark, дешифрует HCI/L2CAP/RFCOMM автоматически). Результат:

(btsnoop_hci.log нужно снимать командой `adb bugreport` а не командой `adb pull`)

- Устройство отвечает на version-запрос значением **`02`** → SPP **протокол v2** (не v1, который был реализован ошибочно по умолчанию).
- Побайтово разобран весь реальный auth-handshake между Mi Fitness и браслетом и сверен с исходником `XiaomiSppPacketV2.java`:
  - **Protobuf-схема оказалась изначально верной на 100%** — все номера полей (`phoneNonce=30`, `watchNonce=31`, `authStep3=32`, `authStep4=33`, вложенные `nonce`/`hmac` и т.д.) совпали с реальными байтами один в один. Ошибка была только во фрейминге, не в протоколе Xiaomi как таковом.

### Безопасность ключа авторизации браслета (2026-09-24)

Auth key Xiaomi не является стабильным значением: он уже несколько раз менялся после переподключения/перепривязки браслета к Mi Fitness. Поэтому **ключ больше не хранится в исходниках Android-приложения** и не должен попадать в Git.

`BandCredentials.kt` не содержит `DEFAULT_AUTH_KEY`: при новой установке приложения ключ по умолчанию пустой, а фактический ключ вводится пользователем в Settings и сохраняется в SharedPreferences. Это позволяет обновлять ключ без пересборки APK и исключает публикацию актуального pairing secret в репозитории.

Старые значения auth key, которые ранее находились в комментариях `task.md`, также удалены из файла. Для работы после очередной смены ключа его нужно заново извлечь через `xiaomi-extractor` и сохранить через настройки приложения.

Следующий шаг: пересборка APK (build v15) и проверка, что существующий сохранённый ключ продолжает использоваться, а новая установка требует явного ввода ключа.

## ✅ Этап B реализован (2026-09-16, build v9) — ожидает теста на реальном устройстве

- **Согласование**: `Health{subtype=2}` (пустой, "get today") → браслет присылает `Health{subtype=1, activityRequestFileIds=<7-байтные fileId>}` (список доступных файлов) → телефон отвечает `Health{subtype=3}` с теми же fileId (запрос) → браслет стримит сырые байты файла по каналу Activity(5) → телефон подтверждает `Health{subtype=5, activitySyncAckFileIds=<fileId>}`.

### Надёжность передачи Xiaomi → backend (2026-09-24)

Обнаружена важная граница первого среза: раньше браслету отправлялся ACK сразу после разбора файла. При недоступном backend это могло удалить файл из очереди браслета до успешной загрузки.

Исправлено:
- распознанные activity-файлы теперь не ACK'аются внутри обработчика Bluetooth;
- их fileId сохраняются как pending;
- после успешной загрузки всех агрегатов в backend SyncHelper вызывает acknowledgeFetchedFiles();
- если backend недоступен или ACK не ушёл, соединение закрывается без подтверждения, поэтому браслет сможет предложить эти файлы снова на следующем цикле;
- неизвестные/неподдержанные типы файлов намеренно не ACK'аются — они остаются доступными для будущего парсера.

Это пока не заменяет полноценную локальную очередь: если приложение получило файл, но сам процесс погиб до загрузки, файл должен снова прийти от браслета, потому что ACK ему не отправлен.

### Корректная обработка ошибки SPP ACK (build v24, 24.09.2026)

После успешного теста сериализации SPP дополнительно закрыта ошибка надёжности, обнаруженная в первоначальном логе v21: writeRaw() проглатывал IOException, поэтому acknowledgeFetchedFiles() мог считать ACK успешным и очистить pendingFileAcks, даже если запись в Bluetooth-сокет фактически завершилась Broken pipe.

Исправлено:
- writeRaw() теперь возвращает Boolean: true только после успешной записи/flush, false при IOException;
- sendEncryptedProtobufCommand() возвращает результат записи;
- acknowledgeFetchedFiles() проверяет результат каждого ACK и при первой ошибке возвращает false, не очищая pendingFileAcks;
- таким образом, при реальном сбое ACK SyncHelper не сообщает ложное подтверждение и браслет сможет предложить неподтверждённые файлы повторно;
- APP_BUILD_TAG повышен до v24 (24.09.2026) - корректная обработка ошибки ACK.

Проверка: предыдущие реальные тесты v23 подтвердили сериализацию SPP и отсутствие Broken pipe; для v24 обязательны git pull && gradlew :app:assembleDebug, установка APK и повторный обычный Sync Now. При успешной передаче ожидаются HTTP 200 и Acknowledged ... activity file(s), а при искусственно/фактически сломанном сокете ожидается false из ACK-пути и отсутствие ложного сообщения об успешном ACK.


### Парсинг реального Xiaomi sleep-файла (build v25, 25.09.2026)

Реальный тест v24 дал точный идентификатор sleep-файла, который присылает этот браслет:

- остальные transport/auth/CRC/ACK части v24 отработали штатно.

Поэтому проблема отсутствия сна локализована не в SPP и не в загрузке файла: sleep-файл успешно приходит и проходит CRC, но до v24 не имел парсера.

Для формата использован источник Gadgetbridge. В его `XiaomiActivityFileId` subtype `0x08` обозначен как `ACTIVITY_SLEEP`, а `SleepDetailsParser` поддерживает sleep details до v4 и для v4 разбирает Summary packet (type=16). В этом пакете первый байт содержит `sleep_index` в старшей тетраде и `wake_count` в младшей тетраде. Это позволяет получить именно количество пробуждений, не используя длительность awake-фазы. См. исходник Gadgetbridge: https://github.com/Freeyourgadget/Gadgetbridge

Изменено в Android:
- добавлен `SleepDetailsParser` для Xiaomi `type=0/subtype=8`;
- добавлены распознавание subtype 8 и сбор `SleepSummary` в `XiaomiBandClassicConnection`;
- `FetchResult` теперь возвращает sleep summaries вместе с activity samples;
- сон привязывается к локальной дате пробуждения, а не к дате начала сна — ночной сон после полуночи попадёт в заметку дня пробуждения;
- `sleep_hours` берётся из Summary packet, `sleep_awakenings` — из `wake_count`;
- эти значения передаются в существующий `/sync`;
- subtype 8 теперь считается распознанным и может быть ACK'нут после успешной загрузки backend;
- build tag повышен до `v25 (25.09.2026) - парсинг Xiaomi сна и пробуждений`.

Пока не утверждаем результат по реальному содержимому v4 до установки v25: локальная сборка из удалённого checkout здесь не запускалась. Следующий обязательный тест на телефоне:

### Ревизия схемы шагов — build v29 — 25.09.2026

В результате fallback-логика v28 иногда выбирала неполные DETAILS вместо полного SUMMARY.

В v29 схема упрощена: для дня хранится только steps_total.
- Android передаёт в /sync единственный параметр steps_total.
- Если Xiaomi DailySummary присутствует, его steps считается авторитетным полным дневным счётчиком.
- Если summary отсутствует, Android использует сумму распознанных минутных samples как fallback.
- Backend /sync и ручной /save записывают только steps_total и проверяют сохранение именно этого значения.
- Старые заметки читаются совместимо: если steps_total отсутствует, backend временно вычисляет его как steps_1 + steps_2; следующая запись уже мигрирует заметку на новую схему.
- Веб-форма показывает одно поле шагов.
