# Промпт: веб-приложение "Sleep Monitor" для ведения дневника самочувствия в Obsidian

## Контекст и цель

Нужно веб-приложение, которое каждый день позволяет быстро занести данные о сне, активности и самочувствии в заметку внутри Obsidian-vault. Источник данных — умный браслет Xiaomi (Mi Band) через приложение **Mi Fitness**, плюс ручной ввод/коррекция субъективных показателей.

Пользователь один (single-user, не multi-tenant). Приложение — личный инструмент, не продукт.

---

## 1. Архитектура

- Сервер: **Ubuntu 24.04**, всё разворачивается через **Docker Compose**.
- Obsidian-vault физически синхронизируется на этот сервер через **Syncthing** (уже настроено, вне зоны ответственности этого проекта).
- Плагин **Local REST API** (coddingtonbear/obsidian-local-rest-api) должен быть включён в vault и обслуживать HTTPS на порту `27124` (self-signed сертификат).
- Поскольку у Obsidian нет официального headless-режима без подписки Obsidian Sync (а тут используется Syncthing, не Obsidian Sync), Obsidian нужно поднять как **реальное Electron-приложение внутри виртуального X-дисплея (Xvfb)** в отдельном Docker-контейнере — по паттерну образов вроде `sytone/obsidian-remote` (Xvfb + noVNC для разовой ручной настройки/логина в плагин через VNC-доступ из браузера).
- Веб-приложение (бэкенд + фронтенд) — отдельный сервис в том же docker-compose, ходит к Obsidian-контейнеру по внутренней docker-сети на `https://obsidian:27124` (или аналогичное имя сервиса), API-ключ Local REST API передаётся через переменную окружения/`.env`, TLS-проверку самоподписанного сертификата отключить для внутреннего запроса (`verify=False` на стороне клиента, т.к. трафик не покидает Docker-сеть).
- **Не писать в vault напрямую по файловой системе** — только через Local REST API, чтобы Obsidian видел изменения через свой live-кеш метаданных, а не спотыкался о рассинхрон при внешней записи файлов.

### Docker Compose — ожидаемые сервисы
1. `obsidian` — headless Obsidian с примонтированным vault-volume (путь к синхронизированной Syncthing-папке) и включённым плагином Local REST API.
2. `app` — бэкенд + отдаваемый им фронтенд (или отдельный сервис фронтенда, на усмотрение реализации).
3. `.env` с переменными: `OBSIDIAN_API_KEY`, `OBSIDIAN_BASE_URL`, `APP_PIN` (пароль входа в приложение), `MIFIT_*` (креды/токен для Mi Fitness, см. раздел 4).

### ⚠️ Деплой: два git-чекаута одного репозитория (актуально с 2026-08-26)
Vault-папка (`10-projects/sleep-monitor`, синхронизируется через Syncthing на Windows-десктоп) и серверная deploy-папка (`~/vsuh-helor-conf/services/opt/sleepmon/` на HRLOR) — это **два независимых git-чекаута одного и того же репозитория** `vsuh/sleepmon` (ветка `master`), а НЕ общий примонтированный путь и не ручная копия файлов.

Следствие: правка `app/main.py` (или любого файла) в vault-чекауте **не появляется** на сервере автоматически. Обязательная последовательность перед любым `docker compose up -d --build app`:
1. В vault-чекауте: `git add`, `git commit`, `git push`.
2. В deploy-чекауте на сервере: `git pull` (сверить `git log -1 --oneline` — коммиты должны совпадать).
3. Только после этого — `docker compose up -d --build app`.

Пропуск шага 2 — самая частая причина "я поправил код, а поведение не изменилось": Docker честно пересобирает образ, но из **старого закоммиченного состояния**, которое уже лежит в deploy-чекауте.

## 2. Структура данных заметки

### Расположение и именование файлов
```
55-sleepmon/<YYYY>/<MM>/<YYYY-MM-DD>.md
```
Например: `55-sleepmon/2026/08/2026-08-26.md`. Папки по году и месяцу создаются автоматически при первой записи (Obsidian Local REST API создаёт недостающие директории на `PUT`).

> Ранее (до 2026-08-16) использовалась плоская схема `55-sleepmon/<YYYY>/<YYYY-MM-DD>.md` без подпапки месяца — заменена на `<YYYY>/<MM>/<YYYY-MM-DD>.md` для более удобной месячной группировки. Реализовано в `_note_path()` (`app/obsidian.py`).

### Frontmatter (YAML)
```yaml
---
project: "sleepmon"
created: "2026-08-26"
related: "[[55-sleepmon/2026/index-08.md]]"
sleep_hours: 7.5          # float, длительность сна в часах
pulse_avg_day: 68         # int, средний пульс за день (бодрствование)
pulse_avg_sleep: 58       # int, средний пульс во время сна (ночной)
steps_1: 3200              # int, шаги за первую половину дня
steps_2: 4100               # int, шаги за вторую половину дня
steps_total: 7300           # int, сумма steps_1 + steps_2 (хранить явно, не только вычислять)
well_being: 7               # int, 0-10, субъективная оценка самочувствия
alco: false                 # bool, был ли алкоголь в этот день
---
```

Это финальная, уже согласованная схема полей — заменяет черновой шаблон `_templates/src/dl-auto.md` (там были нерасшифрованные поля вроде `alco: [true,false]`, тестовый мусор `steps_2: 2` и неясная семантика `steps_1/2`). Не переиспользовать черновик буквально, взять за основу только сам факт существования темплейта.

> **`related` (актуально с 2026-08-26):** больше не хардкодится единой строкой на весь проект. Строится динамически функцией `build_related_link(date_str)` в `app/main.py` как ссылка на **помесячный** индекс: `[[55-sleepmon/<YYYY>/index-<MM>.md]]` (месяц дополняется нулём слева до двух символов). Пересчитывается заново при каждой записи (`/save` и `/sync`), поэтому самоисправляется, если когда-то был записан неверно. Требует, чтобы помесячные индексные заметки (`index-08.md` и т.д.) существовали и содержали dataview-запрос по этой ссылке — сами по себе индексные заметки приложением не создаются.
>
> Более ранняя версия схемы использовала единый индекс `related: "[[55-sleepmon/index]]"` (или `[[sleep-monitor]]` в самой первой версии) — устарело, см. журнал изменений в конце документа.

### Тело заметки
После frontmatter — свободный текстовый раздел для субъективных заметок:
```markdown
## Заметки

(текст пользователя: как спалось, симптомы, комментарии — произвольный markdown)
```

### Границы MVP
Никакой аналитики/графиков/статистики внутри самого веб-приложения не нужно — для этого у пользователя уже есть Obsidian + Dataview. Приложение — это чистый ввод/редактирование данных.

## 3. Пользовательский сценарий (UI/UX)

Однопользовательское веб-приложение, доступное в локальной сети (LAN), мобильный и десктопный доступ.

1. **Вход**: простой общий PIN/пароль на всё приложение (без сложной модели пользователей — один секрет, хранится как хэш в `.env`/конфиге, сессия через cookie).
2. **Главный экран — сегодняшняя запись**:
   - Форма с полями из frontmatter выше: числовые инпуты/слайдеры для `sleep_hours`, `pulse_avg_day`, `pulse_avg_sleep`, `steps_1`, `steps_2` (`steps_total` можно посчитать автоматически на фронте, но сохранять как отдельное поле), слайдер/шкала 0-10 для `well_being`, чекбокс для `alco`, текстовое поле для раздела "Заметки".
   - Кнопка **"Сохранить"** — создаёт/обновляет заметку за сегодня через Local REST API (`PUT /vault/{path}` с полным содержимым, frontmatter + тело). Это единственный путь, которым можно менять `well_being`, `alco` и текст "Заметки" — Android-синхронизация их никогда не трогает (см. раздел про `/sync`).
3. **Навигация по прошлым дням**: простой выбор даты (календарь/список), открывает ту же форму, предзаполненную текущим содержимым заметки этого дня (читается через `GET /vault/{path}`), позволяет править и пересохранять. При переходах между датами, данные берутся из локального кеша, кеш за 5 дней заполняется при загрузке страницы (в фоне).
4. **Массовый бэкфилл**: реализован на стороне Android-приложения (см. раздел 4) — выбор диапазона дат, приложение подряд тянет данные из Health Connect за каждый день диапазона и шлёт их на `/sync`, с отчётом об успехах/ошибках по каждой дате в статус-строке (частичный сбой на одном дне не прерывает весь батч).

## 4. Источник данных: Android Companion App (Health Connect) ✅ РЕАЛИЗОВАНО

От Google Fit API отказались (Cloud API для Fit устарел/ограничен), от прямой интеграции с закрытым API Xiaomi Wear — тоже (нет официального API). Данные получаем через **Health Connect** — системное Android API, куда Mi Fitness сама пишет данные браслета (шаги, сон, пульс), если это явно включено в настройках Mi Fitness («Сторонние приложения» → Health Connect, разрешения Steps/Sleep/Heart Rate).

**Реализация — отдельное Android-приложение** `android_sync_app/` (`com.example.sleepmonitorsync`):
- Читает `StepsRecord`, `SleepSessionRecord`, `HeartRateRecord` из Health Connect за указанный день.
- Шлёт данные на сервер (`POST /sync`) — либо вручную ("Sync Now"), либо в диапазоне дат ("Sync Range" — бэкфилл), либо автоматически в фоне через `WorkManager` (см. ниже).
- Логирование в `SyncHelper.kt`: подробные структурированные логи для каждого шага синхронизации (резолв сервера, чтение каждой метрики, отправка на сервер, итог) — облегчает диагностику при разборе `adb logcat`.

**Фоновая синхронизация:**
- `SyncScheduler.kt` планирует периодический `SyncWorker` через `WorkManager`. Запрошенный интервал — **5 минут** (`ExistingPeriodicWorkPolicy.UPDATE`), но фактический интервал на устройстве определяется системным минимумом Android для periodic work и может округляться до **15 минут** — это ожидаемое поведение платформы, не баг приложения.
- `BootReceiver.kt` переустанавливает задачу после перезагрузки телефона.
- `SyncWorker` синхронизирует последние 2 дня (сегодня + вчера) при каждом запуске — этого достаточно, чтобы поймать ночной сон, попадающий в Health Connect иногда только после пробуждения.

**Резервный сервер:** приложение хранит два адреса (основной + резервный), пробует основной с таймаутом 5 сек, при неудаче на весь прогон переключается на резервный. Оба адреса ведут на **один и тот же** Docker-контейнер `app` (разные внешние точки входа — LAN IP и duckdns через reverse-proxy), поэтому расхождений в поведении между ними быть не должно.

**Важно**: если Mi Fitness перестаёт писать данные (особенно пульс) в Health Connect — это внешняя проблема синхронизации Mi Fitness↔Health Connect, не связанная с кодом приложения. Штатное лечение: отключить/включить интеграцию Health Connect в настройках Mi Fitness и повторить `Sync Now`.

## 5. Технологический стек

- Бэкенд: **Python (FastAPI)**.
- Android: **Kotlin**, Health Connect Client, WorkManager, OkHttp.
- Фронтенд веб-приложения: простой server-rendered Jinja2, адаптивная вёрстка под мобильный экран.
- Хранение PIN-хэша — в конфиге/`.env`, не в коде.
- HTTP-клиент к Obsidian Local REST API — с явным отключением проверки TLS для внутреннего самоподписанного сертификата.

---

## 6. Нефункциональные требования

- Все временные метки — с учётом таймзоны сервера (Ubuntu-сервер, единая для всего проекта; отдельная многочасовая поддержка не нужна).
- Устойчивость к недоступности Obsidian-контейнера: `/sync` при `ObsidianFetchError` прерывается с `502` и **ничего не пишет** (не путает "не смог прочитать" с "заметки нет" — см. журнал 2026-08-16). Форма (`GET /`) при той же ошибке просто показывает пустые поля, ручной ввод остаётся доступен.
- Секреты (PIN-хэш, API-ключ Local REST API) — только через переменные окружения/`.env`, не коммитить в репозиторий.
- Docker Compose должен подниматься одной командой (`docker compose up`) и быть самодостаточным (включая headless Obsidian с уже примонтированным vault и включённым плагином — если первичная настройка плагина требует ручных кликов через VNC, явно задокументировать этот шаг в README).

- Добавлен `ObsidianFetchError` — `/sync` при недоступности Obsidian прерывается с `502`, не создавая заметку с нуля поверх реальных данных.

### 2026-08-25 — шаги не обновлялись, добавлено подробное логирование
- **Баг:** шаги "застывали" на первом значении дня из-за fill-once правила (см. исправление выше) — снято для `steps_1`/`steps_2`, они теперь обновляются на каждой синхронизации.
- Период фоновой синхронизации в `SyncScheduler` изменён с 1 часа на запрошенные 5 минут (`ExistingPeriodicWorkPolicy.UPDATE`); фактически Android округляет до системного минимума ~15 минут — ожидаемое поведение.
- В `SyncHelper.kt` добавлено подробное структурированное логирование каждого шага (резолв сервера, чтение метрик, отправка, итог) — см. раздел 4.

### 2026-08-26 — well_being затирался кешем, related стал динамическим, поймана причина рассинхрона деплоя
- **Баг:** `/sync` использовал `NOTE_CACHE` для чтения "текущего" состояния заметки перед merge-записью. Если `well_being` был отредактирован в обход кеша (например, напрямую в Obsidian, или другим воркер-процессом), `/sync` перезаписывал его устаревшим (нулевым) значением из кеша.
  - **Исправление:** `/sync` теперь всегда читает свежие данные напрямую из Obsidian (`obsidian.get_note_content()`), минуя `NOTE_CACHE`, непосредственно перед merge-записью. Кеш оставлен только для быстрого отображения формы (`GET /`), где устаревшее значение не критично.
- **Изменение:** поле `related` больше не хардкодится единой строкой — строится динамически функцией `build_related_link(date_str)` как ссылка на помесячный индекс `[[55-sleepmon/<YYYY>/index-<MM>.md]]`. См. раздел 2.
- **Найдена причина периодических рассинхронов "код поправлен, а поведение старое":** vault-чекаут и серверный deploy-чекаут — два независимых клона одного git-репозитория `vsuh/sleepmon`, а не общий примонтированный путь. Пересборка Docker без предварительного `git pull` на сервере пересобирает образ из старого закоммиченного состояния. См. раздел 1.
