# Sleep Monitor — задача и план разработки

## 1. Задача проекта

**Sleep Monitor** — личная система дневника сна и самочувствия.

Цель: автоматически получать данные от Xiaomi Smart Band и сохранять дневные показатели в Obsidian, сохраняя возможность ручной коррекции субъективных данных.

Основной сценарий:

1. Xiaomi Smart Band собирает сон, пульс и активность.
2. Android Companion App получает данные с браслета напрямую по Bluetooth SPP.
3. Android агрегирует данные по дням и отправляет их на FastAPI `/sync`.
4. FastAPI читает и изменяет дневную заметку через Obsidian Local REST API.
5. При недоступности сервера синхронизации, Android сохраняет данные в локальной persistent queue и повторяет отправку позже.
6. Файлы активности подтверждаются браслету **только после успешной обработки сервером**.

Проект однопользовательский; встроенная аналитика не является целью — для неё используется Obsidian/Dataview.

## 3. План разработки

### Этап A — стабильный сбор данных с браслета

- Поддерживать secure Bluetooth SPP.
- Авторизовываться на браслете и получать предлагаемые activity-файлы.
- Разбирать как обычные activity-файлы, так и дневной summary Xiaomi `version=5`.
- Использовать `steps_total` из summary v5 как authoritative значение, если оно доступно.
- Не зависеть от insecure RFCOMM.
- Сохранять подробный диагностический logcat.

### Этап B — надёжная доставка на сервер

- Сначала сохранить полученные дневные данные в persistent queue.
- Отправлять очередь на `/sync`.
- Считать данные доставленными только после успешного HTTP-ответа сервера.
- После успешной доставки подтверждать activity-файлы отдельным свежим SPP-сеансом.
- Не удалять элементы очереди при ошибке сервера или ошибке ACK.
- Дедуплицировать даты и идентификаторы файлов.

### Этап C — сервер и Obsidian

- FastAPI предоставляет `/sync` и ручное сохранение.
- Сервер читает существующую заметку перед изменением.
- Android-синхронизация не должна затирать `well_being`, `alco` и свободный текст.
- `steps_total` хранится явно.
- Запись в vault выполняется только через Obsidian Local REST API.
- После записи сервер перечитывает заметку и проверяет сохранённое значение.

### Этап D — эксплуатация

- Фоновая синхронизация через WorkManager.
- Восстановление после перезагрузки телефона.
- Основной и резервный адрес сервера.
- Понятные логи для диагностики Bluetooth, HTTP и ACK.
- Документация должна описывать **текущее**, а не историческое поведение системы.

### Этап E — регрессионные тесты

Для каждого существенного изменения проверять:

1. успешный SPP-сеанс;
2. получение файлов;
3. корректный `steps_total`;
4. HTTP 200 от `/sync`;
5. ACK файлов;
6. запись в Obsidian;
7. поведение при недоступном сервере;
8. повторную отправку persistent queue;
9. завершение сеанса в logcat.

## 6. Принципиальные выводы первых ~30 версий

Первые версии были в основном серией E2E-диагностик Bluetooth, формата Xiaomi-файлов и доставки данных. Подробный журнал каждой версии больше не нужен; важны следующие результаты:

### Xiaomi / Bluetooth

- Прямое подключение к браслету по Bluetooth SPP возможно и работает.
- Для текущей реализации достаточно **secure RFCOMM**; предшествующая попытка insecure RFCOMM удалена.
- Secure SPP иногда требует нескольких попыток подключения. Это наблюдалось и после перезагрузки браслета; успешное подключение на третьей попытке подтверждено.
- После загрузки файлов исходный SPP-сеанс закрывается, а для ACK используется отдельный свежий SPP-сеанс.
- Предсказуемая попытка ACK через уже закрывающийся download socket была исключена.

### Формат данных Xiaomi

- Браслет предлагает несколько activity-файлов.
- Summary `version=5` содержит дневной итог шагов и используется как authoritative источник `steps_total`.
- Отдельные activity-файлы могут быть слишком короткими и тогда пропускаются.
- Суммирование отдельных sample-записей используется как fallback, если authoritative summary отсутствует.

### Доставка

- Простая одноразовая отправка недостаточна: сервер может быть временно недоступен.
- Реализована persistent queue в `filesDir/xiaomi_sync_queue.json`.
- Очередь переживает перезапуск приложения/процесса.
- ACK файлов выполняется только после успешной обработки сервером.
- Ошибка сервера или ACK не должна приводить к потере queued data.

### Backend / Obsidian

- Backend не должен писать markdown-файлы vault напрямую.
- Используется Obsidian Local REST API.
- `/sync` обновляет только машинные показатели и не должен затирать ручные `well_being`, `alco` и заметки.
- `steps_total` стал единым актуальным полем вместо разбиения на `steps_1`/`steps_2`.
- Backend перечитывает заметку после записи для проверки результата.

## 7. Исследование хранения данных браслетом

Практическая проверка с удалением/повторной установкой Mi Fitness показала, что после повторного сопряжения приложение отображало примерно **7–10 дней** данных.

Официальная документация Xiaomi Smart Band 9 Pro указывает ориентир до примерно 7 дней для части health/vitality-данных (сон, пульс, oxygen, stress); для exercise data указан отдельный лимит порядка 100 часов. Это не следует трактовать как универсальную гарантию для каждого типа activity-файлов.

Практический вывод для проекта:

- не полагаться на возможность произвольно запросить любой старый диапазон;
- синхронизировать регулярно;
- использовать persistent queue для решения ситуации с временной недоступностью сервера;
- не считать ACK обычным удалением дневной записи: ACK относится к переданным activity-файлам браслета.

## 8. Важные правила дальнейшей разработки

1. **Не собирать APK в рабочем контейнере проекта.** Сборку выполняет пользователь локально.
2. После любого изменения Android-кода повышать build tag.
3. После каждого изменения кода обновлять этот `task.md` с кратким описанием изменения.
4. После изменений проверять git diff и соответствие документации текущему коду.
5. Не возвращать устаревшие функции только потому, что они были в старой документации.
6. Для Bluetooth сначала диагностировать реальный logcat, а не менять SPP-логику предположительно.
7. Не считать HTTP 200 достаточным для удаления queued data: ACK браслета является отдельным обязательным этапом.
8. При изменении формата данных сохранять backward compatibility при возможности.
9. Документация должна явно отделять подтверждённое E2E-поведение от предположений.

## 16. Android — исправление ночного пульса

В v42 исправлен прямой Xiaomi-путь агрегации пульса:

- DailyDetailsParser уже извлекал heartRate из минутных activity-сэмплов, но aggregateBandSamples() не заполнял pulseAvgSleep, поэтому значение всегда оставалось 0.
- Теперь pulse_avg_sleep рассчитывается как среднее положительных HR-сэмплов внутри интервала bedTime .. wakeupTime из SleepDetailsParser.SleepSummary.
- Для сна, переходящего через полночь, используются все декодированные минутные сэмплы, а не только сэмплы календарного дня пробуждения.
- Добавлен диагностический log: pulse_day=... BPM, pulse_sleep=... BPM.
- Build tag повышен до v42 (27.09.2026) - ночной пульс.
- APK локально не собирался; сборку и E2E-проверку выполняет пользователь.

## 17. Android — защита sleep-данных в offline queue

Исправлено обновление существующей даты в SyncQueue.enqueue():

- повторная загрузка данных того же дня больше не заменяет ненулевые sleep_hours;
- ненулевой pulse_avg_sleep также сохраняется при повторной загрузке;
- sleep_awakenings сохраняется вместе с уже подтверждённой длительностью сна;
- pulse_avg_day и steps_total по-прежнему обновляются новыми значениями;
- новые даты добавляются как раньше.

Это предотвращает потерю уже полученных показателей сна при повторной синхронизации, пока сервер недоступен.

- После изменения Android-кода build tag повышен до v43 (28.09.2026) - защита offline sleep queue.

## 18. Backend — защита pulse_avg_sleep от нулевого перезаписывания

В /sync исправлено слияние ночного пульса:

- ненулевой новый pulse_avg_sleep обновляет значение;
- входящий pulse_avg_sleep=0 больше не затирает уже сохранённый ненулевой ночной пульс;
- pulse_avg_day и steps_total продолжают обновляться как раньше.

Это дополняет защиту локальной persistent queue и предотвращает потерю ночного пульса при повторных sync без доступных HR-сэмплов.

## 19. Android/backend — диагностика авторизации и корректировка merge pulse

После проверки v43 на сервере выявлены две отдельные проблемы:

- Android `login()` раньше считал любой ответ `/login` успешным и мог вернуть пустую/невалидную cookie. Теперь v44 требует HTTP 302 и наличие `session_pin` в `Set-Cookie`, иначе сервер сразу считается неавторизованным.
- В backend после предыдущего изменения `final_pulse_avg_sleep` был рассчитан правильно, но в frontmatter по ошибке использовалась исходная переменная `pulse_avg_sleep`. Исправлено: `/sync` теперь действительно пишет `final_pulse_avg_sleep`.
- Build tag Android повышен до `v44 (28.09.2026) - auth и sleep diagnostics`.

По фактическому Logcat v43: браслет в последней сессии предложил только daily-файлы (`subtype=0`), включая daily summary v5/detailType=1; sleep-файл (`subtype=8`) не был предложен. Поэтому `pulse_sleep=0` в этом запуске вызван отсутствием распарсенного sleep window, а не вычислением среднего HR внутри найденного окна.

## 20. Android — login cookie через reverse-proxy redirect

v44 показал HTTP 200 и отсутствие cookie на `/login`, хотя backend при правильном PIN возвращает 302 с `session_pin`; внешний reverse proxy завершает redirect, поэтому проверка только HTTP 302 была несовместима с production-схемой.

В v45 `SyncHelper.login()` использует OkHttp `CookieJar` и разрешает redirect. Успешная авторизация определяется по фактически сохранённой `session_pin` cookie, независимо от того, завершился `/login` на 302 или конечном 200.

- Build tag повышен до `v45 (28.09.2026) - auth cookie через redirect`.
- После изменения Android-кода APK локально не собирался; сборку выполняет пользователь.

## 24. Android — сохранение пользовательского PIN и URL

- добавлен явный комментарий в коде, фиксирующий write-once семантику дефолтов, чтобы не вернуть регрессию при дальнейших изменениях;
- Android build tag повышен до `v49 (28.09.2026) - сохранение пользовательских настроек`;
- APK в рабочем контейнере не собирался; сборку выполняет пользователь локально.

Важно для проверки: `adb install -r` сохраняет данные приложения, поэтому после установки v49 пользовательский PIN должен остаться прежним. Полная деинсталляция или очистка данных приложения, напротив, создаст настройки заново и установит PIN по умолчанию `1679`.

## 26. Android — получение сна за прошедшую ночь через SPP past fetch

В v51 исправлено главное функциональное отсутствие в прямом Xiaomi-пути: после запроса данных **today** приложение теперь запрашивает также набор **past**.

Что подтверждено исходным протоколом Gadgetbridge:
- `Command{type=8, subtype=1}` — запрос today's activity с `Health.activitySyncRequestToday`;
- после обработки ответа today выполняется отдельный `Command{type=8, subtype=2}` — запрос past, без вложенного `Health`;
- ответ past приходит с `subtype=2` и содержит `Health.activityRequestFileIds`, после чего каждый file ID запрашивается тем же `subtype=3`.

В Android APK:
- добавлен `HEALTH_SUBTYPE_FETCH_PAST = 2`;
- сразу после первого file-offer (`subtype=1`) отправляется `Command(type=8, subtype=2)`, один раз за SPP-сеанс;
- обработчик file-offer теперь принимает и `subtype=1`, и `subtype=2`;
- существующий `SleepDetailsParser` для `activity subtype=8`, versions 1…4, получает шанс реально обработать sleep-файл, возвращая `bedTime`, `wakeupTime`, длительность и awakenings;
- `aggregateBandSamples()` уже относит сон к локальной дате пробуждения, поэтому ночь, начавшаяся вчера и закончившаяся сегодня, попадает в запись сегодняшнего дня;
- `pulse_avg_sleep` продолжает считаться по HR-сэмплам внутри интервала сна, включая участок до полуночи;
- в статус Sync Now добавлен счётчик полученных sleep-файлов;
- build tag повышен до `v51 (29.09.2026) - получение сна за прошлую ночь`.

Почему это закрывает выявленную проблему: до v51 приложение корректно умело разбирать `subtype=8`, но фактически запрашивало только today-набор. Поэтому в реальном Logcat v43–v50 sleep-файл мог отсутствовать вообще. Теперь запрашивается второй, предусмотренный протоколом past-набор; именно туда относится ночная запись, завершающаяся сегодняшним утром.

APK **не собирался в рабочем контейнере** согласно правилу проекта; локальная сборка и E2E-проверка на реальном Band 9 Pro остаются необходимыми для подтверждения фактического появления `sleepSummaries > 0`.


## 27. HCI 29.09.2026 — привязка утреннего теста Mi Fitness

Новый bugreport `bugreport_29092026.zip` содержит HCI snoop `btsnooz_hci.log`. Лог начинается около 09:07 и фиксирует запуск Mi Fitness в 09:09:03.

Для ручного теста пользователя характерный Bluetooth Classic SPP-сеанс начинается в 09:10:01.99 и заканчивается примерно в 09:10:05.11. Внутри него видны SPP v2 preamble `A5 A5`, затем несколько исходящих запросов и крупный входящий поток в 09:10:03.88–09:10:03.89. HCI-записи этого потока имеют Original Length 149, 512, 1004 и 49 байт.

Важное ограничение файла: для больших HCI ACL пакетов Included Length урезан до 15 байт, поэтому содержимое за SPP preamble не сохранено. Из этого конкретного `btsnooz_hci.log` нельзя достоверно прочитать зашифрованный `activityRequestFileIds`, тип `subtype=8` или payload sleep-файла. Новый лог подтверждает реальный SPP-обмен и момент передачи данных, но не является достаточным источником для побайтной расшифровки sleep record.

В качестве binding data для этого сеанса зафиксирован результат Mi Fitness пользователя: сон 8ч27мин, 1 пробуждение, sleep HR 62, интервал 23:24…07:57; steps 188, calories 41, day pulse 80.

Применённое к Android:
- v52 сохраняет найденный v51 путь `today -> subtype=1 offer -> subtype=3 request -> subtype=2 past -> subtype=2 offer -> subtype=3 request`;
- past-запрос теперь отправляется только после валидного today списка file IDs, что точно соответствует обработчику Gadgetbridge;
- в logcat добавлен полный 7-байтовый `rawFileId` для каждого полученного файла и для распарсенного sleep-файла, чтобы следующий E2E-тест можно было однозначно связать с HCI и фактическим record type/version;
- build tag повышен до `v52 (29.09.2026) - привязка HCI и sleep past-fetch`.

APK не собирался в рабочем контейнере; локальная сборка и E2E-тест на Band 9 Pro необходимы для окончательной проверки, что в статусе появляется `sleep-файлов: 1` и запись за 29.09 получает ожидаемые 8.45 часа и 1 пробуждение.

## 28. Android v53 — исправление compile error после локальной сборки

Локальная сборка пользователя после v52 остановилась на compile-time ошибке в `XiaomiBandClassicConnection.kt:591`:

```
Function invocation 'size()' expected.
```

Причина — `activityRequestFileIds` имеет тип protobuf `ByteString`, для которого Kotlin API требует вызов метода `size()`, а не обращение к `size` как к свойству. В той же проверке используется явный вызов `isEmpty()`.

Исправлено:
- `ids.size` → `ids.size()` в диагностической строке;
- `ids.isEmpty` → `ids.isEmpty()` в проверке валидности списка file ID;
- протокол past-fetch и остальная логика получения сна не изменялись;
- build tag повышен до `v53 (29.09.2026) - исправление compile error ByteString`;
- `SyncHelper` и `MainActivity` также получили v53 для однозначной идентификации тестового APK.

После исправления требуется повторная локальная сборка `gradlew :app:assembleDebug`. SDK XML warning из предыдущей сборки не относится к этой compile-time ошибке.

## 29. Android v54 — единая версия и расширенная диагностика sleep-fetch

Изменено также \`MainActivity\`:
- build label и Logcat tag больше не содержат собственного номера версии;
- используются \`AppVersion\` как единый источник версии.


После локального запуска выяснилось, что runtime Logcat всё ещё показывал `XiaomiBandClassic: === v51 ...`: в `XiaomiBandClassicConnection` оставался отдельный hardcoded build tag. Это позволяло одному APK выдавать разные номера версии в разных классах.

В v54 добавлен `AppVersion.kt` как единый источник номера версии:
- номер Android-версии хранится только в `AppVersion.NUMBER`;
- build label и component Logcat tags строятся из него;
- следующие изменения версии не требуют поиска старых строк `vN` по нескольким файлам.

Одновременно подготовлена диагностика следующего E2E-запуска:
- Logcat должен явно показывать health subtype и размер списка file IDs;
- после fetch должны быть видны количества полученных, ошибочных, неподдержанных и sleep-файлов;
- для неподдержанных activity-файлов должны сохраняться их type/subtype/detail/version, чтобы отличить отсутствие sleep-файла на браслете от непройденного parser path.

Тест с данными пользователя 29.09.2026 пока не считается доказательством отказа past-fetch: Mi Fitness синхронизировал браслет около 09:10, а APK выполнил свою попытку только около 11:52. Если Mi Fitness уже подтвердил и удалил соответствующий activity-файл, повторно получить его с браслета нельзя. Следующий E2E-тест должен выполняться до синхронизации этого утра Mi Fitness либо на браслете с ещё не забранной ночной записью.
